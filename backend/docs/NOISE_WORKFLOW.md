# Noise investigation and context policies

**Implemented but unverified — September 11, 2026.** This delivery used static source
review and diff formatting only. No tests, syntax/lint checks, servers, SDK probes,
browser acceptance or model calls were run. See the [assigned plan](NOISE_PLAN.md).

## What the user does

1. Chat normally, then open a message's **View trace** or **Conversation traces**.
2. Select the trace and use **Investigate noise and prevent recurrence** to describe
   the issue. This explicitly calls the existing local Ollama model once. It returns
   cited findings, confidence, evidence gaps and supported policy suggestions. A tool
   defect, missing evidence or no issue does not produce a context-policy draft.
3. Relevant evidence links appear above the explorer. The full span hierarchy is
   collapsed after a finding, remains expandable, and original evidence is unchanged.
4. Review **Source versions and approvals**. Assign version families, versions,
   current/superseded status, approvals, topics and protected sources using actual
   source information. These are your annotations, not conclusions generated by AI.
5. In Documents, choose suggested rules and **Review cleanup**. The review shows the
   current sources, hashes, retained replacements, exclusions and project/environment
   scope. For topic matching, enter the requested topic. Existing active rules are
   carried forward. A review that excludes nothing more cannot be applied.
6. Review the actual affected sources, then click **Apply filter**. This explicit user
   approval does not require trial runs. The backend checks the revision, unchanged
   source/metadata snapshot, previous active policy and exact selection again. It
   records `user_approved_filter`, never verified task success. Applying makes no model
   call and runs no task. Other conversations in the same project/environment also use
   the policy on subsequent current retrievals; other scopes are unaffected.
7. Continue chatting and inspect **Actual context delivered**. **Undo filter** restores
   the previous active policy (or no policy) for the current activation. Source files,
   original traces, explicit source reads and saved messages remain available.

See the [duplicate-PDF walkthrough](DATA_NOISE_DEMO.md) for a concrete data-noise case
that does not depend on a defective renderer. A duplicate can waste context even when
the answer remains correct; causality must not be invented.

## Optional trial workflow

The existing trial route remains available in **Policies and optional trial workflow**.
In Documents it is optional; standard-tool policies still use this route. No generated
tool/retrieval-code repair gate has changed.

1. Under a supported finding, expand **Optional: evaluate a draft with four trial runs
   first** and save the selected rules as a named draft (standard tools show the draft
   form directly). Create previews for the original, fresh, unaffected and historical
   cases, selecting the sources each case must retain. Preview tables show retained
   and excluded sources, reasons and unresolved metadata.
2. Choose **Use this preview in my next message**. Epoch opens the chat with a visible
   trial banner. Nothing runs until you submit a message. Ask Hermes to retrieve
   documents with the preview's purpose/version/topic. Trials use the candidate only
   for that submitted message and never publish it. Trial runs can use the normal
   granted tools; choose a safe request and do not blindly replay previous writes.
3. Inspect the trial trace and output. Record its trace ID, your passing/failing
   assessment and notes against the exact preview. The backend checks that the trace
   belongs to that conversation, the operation used that preview, execution completed,
   and a recorded selection matches it while retaining the declared required sources.
4. After four distinct passing trial traces, activate the reviewed policy while idle.
   Original and fresh cases must actually exclude something; a no-op filter cannot
   satisfy those gates. Sources, metadata and revision must still match the previews.
5. Continue chatting. Ordinary document retrieval uses the active project/environment
   policy and records the decisions. **Roll back this activation** restores the prior
   active policy (or no policy) for the current publication. No task is automatically
   rerun. Keep the previous activation and rollback records for provenance.

Activations through this trial route are labeled **manual trials recorded**, distinct
from **user-approved filter** on the direct Documents route. Neither independently
establishes task success. This is a host-defined rule engine with user approval; it does
not replace the existing generated-code repair system or weaken that system's gates.
An earlier failed or ambiguous assessment is retained even after a later passing trial.

## Supported selection semantics

| Rule | Behavior | Preservation boundary |
| --- | --- | --- |
| `deduplicate` | Consolidate identical content with equivalent kind and metadata | Different version/authority metadata remains distinct; originals remain readable |
| `prefer_current_approved` | In a declared version family, exclude explicitly superseded sources when exactly one approved current source exists | Unknown status and conflicting/missing approvals remain visible; protected sources stay |
| `match_topic` | For a tool request specifying a topic, exclude sources declaring different topics | Untagged sources stay; no topic means no topic filtering |

The selector never edits document sections, summarizes away required facts, deletes
logs/files, infers approval from modification dates, or filters by hard-coded filenames,
invoice IDs or fixture labels. If filtering would remove every source, it is refused
and all candidates remain with a warning. These rules are deliberately bounded; arbitrary
semantic paragraph deletion and automatic cross-run root-cause proof are not implemented.

`documents.list` accepts optional `purpose` (`current`, `historical`, `all`), `version`
and `topic`. Empty arguments remain accepted and default to current context. Historical,
all and explicit-version requests bypass the current-context filters. They expose the
authorized catalog rather than guessing which historical source the user intended.
`documents.read` with an explicit asset ID preserves the original read, including access
to a source excluded from the current catalog. Existing content limits/truncation flags
remain; filtering does not fix a broken renderer or remove required content to make it fit.

For standard-tool chats, `runbooks.read` uses the pinned policy and its existing
current/historical/version arguments. Ambiguous current authority fails explicitly when
the current-approved rule cannot select one document. Existing generated runbook repairs
retain ownership of their selection path; activating a competing policy is refused.
Release/repair runs without an ordinary-chat policy pin preserve their original behavior.

Source metadata is kept separately by project, environment, chat/source identity and
content hash. Unambiguous annotations can be reused for matching content in another chat
of the same project/environment. Conflicting annotations are not guessed. Changing source
metadata deactivates the scope's current policy and invalidates old reviews. Set metadata
before creating the cleanup review or trial previews. This is local single-user workspace scope,
not new multi-user authentication.

## Evidence, persistence and worker lifecycle

The existing data directory gains `context-policies.sqlite3`, created on normal startup:

- `noise_records`: issue analyses, immutable drafts, source annotation changes,
  cleanup reviews, previews, user assessments, activations and rollback history.
- `context_scopes`: revision, active policy pointer and source annotation index for
  each project/environment. The pointer is authoritative; a draft record is immutable.
- `context_decisions`: operation, tool/query, pinned policy/revision, candidate IDs and
  hashes, source metadata, retention decisions and the actual returned content/hash.

The same selection function powers preview and actual tools. A trial submission pins
the preview's policy after checking its source/metadata snapshot. Normal submissions pin
the current active policy. Policy identity/revision enters the saved chat operation and
the Neatlogs workflow attributes. Tool results carry selection references; local issue
analysis can also read bounded selection excerpts tied to the operation root span.
Those are observed tool-boundary records, not private model reasoning or proof of causality.

Activation, rollback and metadata changes require idle execution and discard the warm
worker. A subsequent message starts with its updated policy pin. Trial identity also
prevents reuse across different candidate previews. Old user/assistant messages remain
saved; no debugger history is silently inserted into Hermes. Noise already contained in
visible chat history is not automatically rewritten. Explicit source reads can bypass
catalog filtering, so recurrence prevention must be assessed on the intended workflow.

Cleanup reviews include the original source snapshot, baseline selection, proposed
selection and newly excluded IDs. Apply atomically writes a new immutable policy,
activation receipt and scope revision. Concurrent, stale or no-effect approvals fail
without updating the active policy. The workspace returns the current activation even
when it is older than the bounded history, so Undo stays accessible. Rollback is for
the current activation; it is not an arbitrary chain of historical undos.

All mutations use exact `client_request_id` identities; changed payloads conflict.
Publication/metadata actions also check the current revision. The browser journals pending
actions and offers explicit retry after uncertain acknowledgements. Reads/reloads do not
submit analyses, replay trials or publish policies. Interrupted analyses become failed on
restart. The UI shows bounded recent history; records remain stored and readable by ID.

## If the local investigation fails

**Outcome/action consistency — September 11:** the next user result identified the
specific failure: the model selected `tool_defect` while proposing context filters.
The request schema now uses two complete `anyOf` alternatives. One permits only the
`context_noise` outcome and its supported rule list; the other permits the remaining
outcomes and constrains `rules` to the literal empty array. Shared definitions stay at
the root. String-bound simplification and snapshot citation enums are still applied.
This follows the converter's [union and constant handling](https://github.com/ggml-org/llama.cpp/blob/master/common/json-schema-to-grammar.cpp).

The flat response contract still appears once in the prompt, with explicit outcome/rule
instructions, to avoid doubling prompt content. The existing Pydantic, citation and
cross-field checks still reject contradictory or malformed responses. No answer is
silently edited to remove bad rules. This uses one model call with no automatic retry.
New records identify `noise-analysis-v4` and `noise-outcome-rules-v1`.

For a valid `tool_defect` finding, the UI displays the cited diagnosis and an **Open PDF
debugger** link in document conversations. It opens the same conversation's saved
evidence; review the available **Fix PDF tool** action there. Opening the link does not
start repair or guarantee a particular repair is eligible. Insufficient-evidence and
no-issue results have their own next-step notices, and no filter-draft form.

Restart the normal backend, refresh the frontend, and click **Try investigation again**.
Expected for this PDF case, if the model again identifies a tool defect: a saved cited
answer with `rules: []`, no filter proposal and a Debugger link. Also manually confirm a
real context-noise case can still propose supported rules. Existing failed analyses stay
failed in history. No `.env` change, dependency or migration; implemented but unverified,
with no tests, model calls, server runs or browser acceptance performed by the developer.

**Rejected-answer follow-up — September 11:** the user's subsequent two requests returned
HTTP 200 and produced output in the Ollama log. Their saved records only retained
`invalid_model_answer`, not the failed check or answer text; the precise cause of those
historical rejections cannot be reconstructed. HTTP success alone is not validated
investigation success.

New requests distinguish `ollama_output_limit`, `ollama_incomplete`, `ollama_empty_answer`,
`invalid_answer_json`, `invalid_answer_shape`, `invalid_answer_schema`, `invalid_citation`
and `invalid_policy_proposal`. **Failure details** shows bounded completion metadata,
JSON line/column, schema field/type errors or citation IDs as appropriate. It does not
save raw rejected model text or the model's thinking field. Errors identify the failing
constraint; answers are not silently shortened, citations remapped or rules discarded.

The parser accepts either a plain JSON object or one complete `json`/unlabeled Markdown
code fence containing that object, because the installed runner permits that wrapper.
Surrounding prose, partial JSON, extra objects and wrong field types remain rejected.
The sampling schema now constrains citation choices to the current snapshot's actual
IDs, with the existing host citation check retained. Full answer validation and policy
publication gates remain unchanged. New requests use `noise-analysis-v3` or
`trace-question-v3` and `ollama-scoped-citations-v2`.

Restart the backend, refresh the frontend, and choose **Try investigation again** using
the same trace; the PDF task need not be rerun. If it fails, inspect the specific message
and **Failure details**. Keep the existing model and `.env`; no settings or migration are
required. These changes were reviewed statically only, with no live model acceptance.

**Grammar rejection fix — September 11:** the user's retry returned HTTP 400 with
`Failed to initialize samplers: failed to parse grammar`. The desktop Ollama log shows
a repetition-complexity rejection and generated `char{1,2000}` rules for summary,
explanations and missing-evidence text. The current request passed the full Pydantic
string-length constraints into the grammar compiler.

Both noise analysis and trace questions now use a separate sampling schema that omits
`minLength` and `maxLength` on strings, including strings inside definitions and arrays.
JSON structure, required fields, enums, array limits and references stay constrained.
The full schema remains in the prompt; the unchanged Pydantic validators enforce all
length limits on the returned answer. Citation checks, allowed rules, output budgets
and publication gates remain unchanged. An invalid answer is rejected, not truncated
into acceptance. New noise records and trace-question usage record the schema version;
prompt versions distinguish new requests from historical attempts.

This is a client compatibility fix for the observed grammar limit, consistent with
the upstream [bounded-string grammar report](https://github.com/ggml-org/llama.cpp/issues/27087)
and Ollama's [schema-and-validation workflow](https://docs.ollama.com/capabilities/structured-outputs).
It is implemented but unverified: restart the normal backend and choose **Try
investigation again**. No `.env` edit, model download or Ollama update is required by
this change. Expected: this grammar rejection disappears and the investigation either
returns validated findings or a separate, specific error. Confirm that outcome manually.

The earlier message, "Ollama rejected the request. Check the local model and available
memory", was a generic HTTP failure message, not a memory diagnosis. The shared client
now reads a bounded JSON `error` field before rejecting the response. New failures show
the HTTP status, endpoint, a bounded provider message and an error code. Common credential
patterns are redacted; response headers, request bodies and non-JSON error pages are not
copied into diagnostics. Provider text is escaped in the UI. Trace questions use the same
handling. Timeout, transport and invalid-answer failures have separate messages.

| Observed detail | Next manual action |
| --- | --- |
| `ollama_memory`, with an explicit allocation/memory error | Free memory or unload another Ollama model, then retry |
| HTTP 400/422 or a schema/grammar error | Keep the exact detail for debugging the request; changing the PDF source does not address this failure |
| HTTP 404 | Compare `ollama list` with the existing `EPOCH_TRACE_MODEL`, and check the configured API address |
| HTTP 429/503 | Wait for the local server to become ready before retrying |
| HTTP 500 without a specific cause | Inspect the Ollama server log; memory is not established by the status alone |
| `ollama_unavailable` / `ollama_timeout` | Check that Ollama is running / inspect generation duration and the existing timeout setting |

After restarting the updated backend and refreshing the frontend, choose **Try
investigation again** beneath the failed result. This creates a new request with the
same trace and issue, retaining the failed attempt. It never activates a policy. Refresh
alone does not run inference. Older saved failures cannot recover the response detail
that the previous client discarded; their original messages remain unchanged.

On Windows, Ollama's desktop server log is normally at
`$env:LOCALAPPDATA\Ollama\server.log`; if Ollama was started in a terminal, inspect that
terminal instead. An empty or older log cannot establish the cause of a current failure.
The implementation follows Ollama's [JSON error response contract](https://docs.ollama.com/api/errors).
The earlier diagnostic fix required no model/schema change, extra dependency, `.env`
edit or migration. The subsequent sampling-schema fix is described above. Live retry,
failure rendering and success-path acceptance remain unexecuted by the developer.

## HTTP and CLI

All endpoints below are under `/api/chats/{chat_id}/noise`:

| Method/path | Purpose |
| --- | --- |
| `GET /` (without trailing slash) | Sources, annotations, current revision/policy and recent records/decisions |
| `GET /records/{record_id}` | Saved record belonging to the conversation |
| `GET /decisions/{record_id}` | Full recorded candidate/selection/delivered context, loaded on request |
| `POST /analyses` | Explicit issue investigation through local Ollama |
| `POST /sources/metadata` | User annotations with source hash and expected revision |
| `POST /policies` | Draft selected supported rules from a cited analysis |
| `POST /cleanup-reviews` | Documents only: snapshot a suggested filter, affected sources and carried-forward rules |
| `POST /cleanup-reviews/{id}/apply` | Apply after user review if the exact source/metadata/revision snapshot is unchanged; no trial requirement |
| `POST /policies/{id}/previews` | Immutable selection preview and required-source criteria |
| `POST /policies/{id}/validations` | Record an assessment of a real preview-bound trial trace |
| `POST /policies/{id}/activate` | Publish after four passing, unchanged cases |
| `POST /rollback` | Restore the previous pointer for the current activation |

`POST /api/chats/{id}/messages` additionally accepts optional `context_preview_id`.
It participates in the existing message retry identity. Old clients can omit it.
The full field contracts are in [noise_contracts.py](../src/epoch_backend/noise_contracts.py).

From `backend`, read without invoking a model:

```powershell
uv run --frozen epoch-backend --env-file .env noise CHAT_UUID workspace
uv run --frozen epoch-backend --env-file .env noise CHAT_UUID record --record-id RECORD_UUID
```

For explicit mutations, save the exact JSON body (including a UUID `client_request_id`)
in a local file. The CLI supports `analyze`, `metadata`, `draft`, `review`, `apply`,
`preview`, `validate`, `activate` and `rollback`. Preview/validate/activate require
`--policy-id`; apply requires `--review-id`.

```powershell
uv run --frozen epoch-backend --env-file .env noise CHAT_UUID analyze --json-file issue.json
uv run --frozen epoch-backend --env-file .env noise CHAT_UUID review --json-file cleanup-review.json
uv run --frozen epoch-backend --env-file .env noise CHAT_UUID apply --review-id REVIEW_UUID --json-file cleanup-apply.json
uv run --frozen epoch-backend --env-file .env noise CHAT_UUID preview --policy-id POLICY_UUID --json-file preview.json
```

Example `issue.json` shape (replace placeholders with actual identities):

```json
{"client_request_id":"REQUEST_UUID","trace_id":"32_CHARACTER_TRACE_ID","issue":"Why did this task use superseded guidance?"}
```

Example `preview.json` shape:

```json
{"client_request_id":"REQUEST_UUID","case":"original","purpose":"current","version":null,"topic":null,"required_ids":["ACTUAL_REQUIRED_SOURCE_ID"]}
```

Example `cleanup-review.json` (use the current workspace revision and an answered
context-noise analysis that actually proposed this rule):

```json
{"client_request_id":"REVIEW_REQUEST_UUID","analysis_id":"ANALYSIS_UUID","expected_revision":0,"title":"Consolidate duplicate context","rules":["deduplicate"],"topic":null}
```

Read the returned review, including `ready`, `blocked`, `selection`, `newly_excluded_ids`
and `snapshot.revision`. Only after reviewing those sources, submit `cleanup-apply.json`
with a new request UUID and that exact reviewed revision:

```json
{"client_request_id":"APPLY_REQUEST_UUID","expected_revision":0}
```

The returned activation ID can be supplied to the existing rollback command. Use the
same request UUID and body for an uncertain retry, not for a different action. A stale
review requires a newly created review and a fresh explicit approval.
