## Shared interfaces

`Sandbox(path, task_id: str, run_id: str)` owns one SQLite database per run. `initialize(scenario="control", project_id="demo", release="1.0", grants=None)` seeds a sandbox; `reset(...)` is explicit developer-only setup. Scenarios: `control`, `broken_checklist`, `missing_lookup`, `outdated_context`. Reopening does not reset effects. `metadata()` returns setup to trusted code, `snapshot()` returns inspectable simulated state, `evaluate()` returns trusted checks, and `events(after=0)` returns persisted increasing-sequence events. `record_event(type: str, payload: dict)` appends an event with task/run identity and time.

Sandbox operations: `create_ticket(title, release, idempotency_key)`, `create_checklist(ticket_id, title, items, idempotency_key)`, `send_message(channel, text, links, idempotency_key)`, `list_tickets()`, `list_checklists()`, `list_messages()`, and `read_runbook(purpose="current", version=None)`. Operations return JSON dictionaries or lists and throw `SandboxError(code, message)` for expected failures. Every returned business object/reference is labelled simulated. Per-run setup includes expected release checklist content and QA destination; trusted evaluation checks actual state against these criteria. Registry validation enforces operation/project grants before business access.

`ToolRegistry(sandbox)` provides `discover_tools() -> dict`, `describe_tool(name: str) -> dict`, and `invoke_tool(name: str, arguments: dict) -> dict`. Facade responses use `{ok: bool, result: ..., error: {code, message}}` with exactly one result/error. Registry retains discovery, description, calls/results/errors and context events; the MCP wrapper adds no business behavior. Fixed tool names are `tickets.create`, `tickets.list`, `checklists.create`, `checklists.list`, `messages.send`, `messages.list`, `runbooks.read`. Directory data exists, but no owner-lookup tool is provided.

The MCP subprocess entrypoint is `python -m epoch_backend.mcp_server --database PATH --task-id UUID --run-id UUID`. It opens an already initialized sandbox, never resets/seeds one, and writes protocol-only output to stdout. Administrative functions are never registered. Use the official MCP Python SDK with a pinned compatible major and test actual protocol discovery/invocation; no hand-written protocol imitation.

Verified selection: official MCP SDK 1.29.1, constrained to the supported `>=1.28,<2` series. [The supported v1 SDK](https://github.com/modelcontextprotocol/python-sdk/tree/v1.x) supplies the server and test client. Installed Hermes commit `7166071fcaadb36df26f6d753dda97da6b5d699e` supplies the real agent; each run uses its existing environment and configured route. The adapter disables optional lazy tool wrapping and MCP resource/prompt utilities through documented local-source configuration, preserving the exact three-function facade.

The existing model route is `openai-codex` / `gpt-6-astra` through `https://chatgpt.com/backend-api/codex`. Only the existing credential is read into the worker's memory; it is never copied into project configuration, logs or MCP environment. [OpenAI authentication documentation](https://learn.chatgpt.com/docs/auth) describes ChatGPT sign-in for Codex; Epoch compatibility is established by the installed Hermes execution evidence, not inferred from that documentation.

HTTP execution will require an explicit structured release specification submitted separately from Phase 1 intake. It does not infer arbitrary checkpoints or create automatic corrective instructions. Real execution status and verification are distinct: executor text cannot mark an unmet outcome complete. Runs have time/turn limits, one active execution per server, cancellation and interrupted-run recovery; model credentials are never accepted from the browser or placed in traces.
